# Dependencies: overrides, audits, and Dependabot failure modes

This is the detailed reference for the dependency settings in `pnpm-workspace.yaml` (`overrides`, `audit.ignore`) and `package.json` (`engines.node`), and for the ways Dependabot fails on this repository, moved out of `AGENTS.md`.

## Node.js floor (`engines.node`)

Node.js 22.22.0 or later is required: on Node 22, astro 7.4's CLI exits with an error below 22.22.0, and `engines.node` records that floor. Some dependencies declare a higher minimum (`@astrojs/prism` 4.1.1 declares 22.23.4) without checking it at run time. pnpm 12.9.1 neither warns about nor rejects an `engines` mismatch by default, whether in this repository's field or a dependency's; only `engineStrict` makes it fail, on both alike. Raise `engines.node` together with the astro update that raises the CLI floor.

## Overrides

The `overrides` entries in `pnpm-workspace.yaml` pin transitive dependencies to address vulnerabilities and keep Dependabot alerts at zero. Do not remove them until patched versions have propagated through the upstream dependency graph. pnpm applies overrides to peer ranges too: `postcss@<8.5.23` makes the lockfile record `postcss: ^8.5.23` as the peer range of `postcss-nested`, which declares `^8.2.14`. Remove such a pin before moving to another major of the pinned package, which the rewritten peer ranges would not accept.

The `@swup/plugin@<4` override prunes a dependency path rather than pinning a patched version. `@swup/parallel-plugin` and `@swup/route-name-plugin` still declare `@swup/plugin@^3.0.0`, and version 3 lists its build toolchain (microbundle, prettier, and shelljs) as runtime dependencies, so forcing version 4 keeps that toolchain out of the tree.

The `katex@<0.18.2` override also forces a version outside the consumers' declared range. `rehype-katex` and `micromark-extension-math`, which `remark-math` pulls in, still declare `katex@^0.16.0`, and no 0.16 release contains the fix for GHSA-238p-pmpm-9mq7. The override moves them to the same 0.19 line as the direct `katex` dependency, which supplies `katex/dist/katex.css`, so the HTML rendered at build time and the stylesheet come from one version. KaTeX 0.18 renamed layout classes such as `base` and `strut` to `katex-base` and `katex-strut`, so 0.16 markup does not match the 0.18 stylesheet. Remove the override once both consumers accept a patched version.

The `postcss-selector-parser@<7.1.6` override likewise forces a version outside a consumer's declared range, across a major version. `@tailwindcss/typography` pins `postcss-selector-parser@6.0.10` exactly, while only 7.1.6 fixes GHSA-rj75-hqrm-r3gf. The other consumer, `postcss-nested@7`, which `@expressive-code/core` pulls in, declares `^7.0.0`, so for it the entry is only a lower-bound pin. Both consumers run only at build time on the site's own CSS, and the override leaves `dist` byte-identical. Verify any change to this override the same way: build before and after with `.astro`, `node_modules/.astro`, and `node_modules/.vite` removed, and compare `dist`. Once `@tailwindcss/typography` declares a 7.x range, the entry becomes an ordinary lower-bound pin.

pnpm matches an override key that carries a version selector, such as `"fast-uri@>=3.0.0 <X": "^X"`, against the range each consumer declares (a semver intersection test), never against the installed version, so the key keeps matching `ajv@8.20.0`'s `fast-uri@^3.0.1` after X is installed. What keeps the pin from moving is the lockfile: the locked X already satisfies the target `^X`, and pnpm re-resolves an override only when its entry changes. When a later advisory widens its affected range, raise the target, and the selector with it so the key still documents the advisory's range: the changed target is what makes `pnpm install` re-resolve the dependency and exclude the old version. The consumers keep declaring permissive ranges — `ajv@8.20.0` still accepts `fast-uri@^3.0.1` — so these direct pins stay necessary even after the consumers are updated.

## Fixing a transitive alert by hand

Dependabot often cannot fix an alert on such a transitive dependency. pnpm 12 refuses its version-pinned `pnpm update <package>@<version> --lockfile-only` for a package that is not a direct dependency, and Dependabot then retries without a version. Security updates do not use the `cooldown` in `.github/dependabot.yml`, but the two phases of the run resolve that retry differently. The update check passes no release-age setting, so pnpm's own `minimumReleaseAge` default (1440 minutes since pnpm 11, non-strict) applies and can hold back a release published within the last day, while the file update passes `--config.minimum-release-age=0` and takes the newest release. When the two disagree, the run fails, with `dependency_file_not_resolvable` when the check settled on an older fixed release; `docs/dependency-update-investigation.md` records the evidence.

Fix such an alert by hand. Run `pnpm update <package> --lockfile-only --config.minimum-release-age=4320` without a version, which moves the pin within the consumers' ranges to the newest release at least three days old. The three days are this repository's own margin, the same length as the patch cooldown for version updates; Dependabot applies no such delay to security updates. If every fixed release is younger than that, `pnpm update` keeps the pin on a vulnerable release, and once the override requires a fixed release, the `pnpm install` below fails resolution, because an explicit value makes pnpm strict and no release in the overridden range is old enough; wait or lower the value. Then raise the matching override, or add one in the same shape when the package has none, run `pnpm install` with the same `--config.minimum-release-age` so the re-resolution keeps that release and the lockfile records the override, and confirm that `pnpm audit` exits 0 and reports nothing beyond the entries in `audit.ignore`.

## `audit.ignore`

`audit.ignore` in `pnpm-workspace.yaml` holds GHSA-gcqx-w48m-w2h4 in `deepmerge`, which only `@sveltejs/vite-plugin-svelte` uses. The advisory lets a `__proto__` key in a merged source set the prototype of objects in the merge result. No release fixes it: 4.3.1 is the latest, and the maintainer declined to fix it in TehShrike/deepmerge#273. The plugin does run the affected `mergeObject()`, so its Dependabot alert is dismissed as a tolerable risk rather than as not used, but it merges only its own defaults and values with the options `@astrojs/svelte` passes from `astro.config.mjs` while Vite resolves its config, so no outside data reaches it, and no deepmerge code reaches `dist`. Do not override it with a patched fork: the forks on npm are new single-maintainer packages, a larger supply-chain risk than this advisory poses to a build-time merge of the repository's own config. Remove the entry once the advisory is withdrawn, a deepmerge release fixes it, or `@sveltejs/vite-plugin-svelte` stops depending on deepmerge, as sveltejs/vite-plugin-svelte#1415 proposes.

When an advisory is withdrawn, GitHub drops its alert without a dismissal, but the entry stays: `pnpm audit` does not warn about stale entries, and `pnpm audit --fix` prunes them only when `audit.ignorePrune: true` is set in `pnpm-workspace.yaml` (pnpm 12.0.0 or later, off by default; verified with pnpm 12.9.1), so remove it by hand. Edit `audit.ignore` by hand: on pnpm 12.9.1, `pnpm audit --ignore` appends the ID to an existing `audit.ignore` list but re-renders that block, dropping the comments inside it and the blank line after it, while the rest of the file is preserved. The explanatory comment therefore sits above the `audit:` key, where the writer leaves it.

## Removing an optional peer of Vite

Once pnpm has resolved one of Vite's optional peers, such as `sass`, `stylus`, or `terser`, the lockfile keeps it after nothing depends on it. `pnpm install`, `pnpm update`, `pnpm dedupe`, `--fix-lockfile`, and `"-"` removal overrides all leave it installed. To drop one, delete both `pnpm-lock.yaml` and `node_modules` before running `pnpm install`, because pnpm otherwise reuses `node_modules/.pnpm/lock.yaml`, and confirm with `pnpm why <package>` that it is gone.

## `ERR_PNPM_BROKEN_LOCKFILE` on Dependabot PRs

If every CI job on a Dependabot PR fails with `ERR_PNPM_BROKEN_LOCKFILE` and a duplicated mapping key, the cause is the GitHub test merge rather than the PR itself. An older PR and `main` have both added the same transitive dependency to the lockfile, and the textual merge produces the duplicate key. Confirm that the lockfile at the PR head is valid by using `git show origin/<branch>:pnpm-lock.yaml` and searching for the affected key. If the user explicitly authorizes the external comment, post `@dependabot recreate` as a human user. Do not repair and push the lockfile manually: after an extra commit is pushed, Dependabot stops automatically rebasing that PR. Commands from a bot identity backed by `GITHUB_TOKEN` are rejected, so this operation cannot be automated that way.
